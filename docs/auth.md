# 실제 로그인 — 설계

## 왜 필요한가

지금은 **익명 로그인만** 씁니다. 규칙 입장에서 모든 접속자는 똑같은 익명
계정이라, "누가" 요청했는지 구분할 수 없습니다. 그래서 지금까지 남은
한계가 전부 여기서 나옵니다.

| 한계 | 지금 상태 |
|---|---|
| 회원 명단 읽기 | **막을 수 없음.** 익명이라도 로그인만 하면 `kv/members`를 읽습니다. 앱 화면에서 가릴 뿐, 스크립트로는 그대로 보입니다. |
| 소유자 ↔ 운영자 구분 | **앱 안에서만** 유효. 운영자 비밀번호를 아는 사람이 앱을 거치지 않고 Firestore를 직접 두드리면 명단을 갈아끼울 수 있습니다. |
| 비밀번호 무차별 대입 | 서버가 시도 횟수를 세지 못합니다. 지금 잠금은 그 브라우저 localStorage 안에서만 돕니다. |
| 기록·통계 보호 | 세션 문서를 읽을 수 있으면 그날 참가자와 게임 수가 그대로 보입니다. |

비밀번호를 아무리 잘 숨겨도(지금 구조는 해시조차 안 내려갑니다) **읽기
권한 자체가 열려 있으면** 소용이 없습니다. 자물쇠는 튼튼한데 창문이
열려 있는 상태입니다.

---

## 갈림길 — 회원도 계정을 만들어야 하는가

이게 전부를 가릅니다. 나머지는 여기서 따라옵니다.

### 갈래 A — 운영자·소유자만 계정을 만든다

- 소유자와 운영자는 **이메일/구글 로그인**으로 진짜 계정을 갖습니다.
- `clubs/{club}/roles/{uid}` = `{ role: 'owner' | 'admin' }`
- 규칙이 이 문서를 보고 판단합니다. 앱을 거치지 않아도 막힙니다.
- **회원·게스트는 지금 그대로** — 이름 고르고 한 글자 넣으면 들어옵니다.

무엇이 해결되나
- ✅ 소유자 ↔ 운영자가 **DB 수준에서** 진짜로 갈립니다. 명단 통째 교체는
  소유자 계정이 아니면 서버가 거부합니다.
- ✅ 비밀번호 무차별 대입이 사라집니다 — 비밀번호 대신 계정으로 들어옵니다.
  probe·PBKDF2 구조를 통째로 걷어낼 수 있습니다.
- ❌ **회원 명단 읽기는 여전히 안 막힙니다.** 회원이 익명인 이상 규칙이
  "이 사람이 이 동호회 회원인가"를 물을 방법이 없습니다.

비용
- 운영자 2~3명이 계정을 만들면 끝. 회원들은 아무것도 안 바뀝니다.
- 앱 변경 범위: `auth.js`, `gate.js`, 규칙. 중간 규모.

### 갈래 B — 회원도 전부 계정을 만든다

- 모든 회원이 이메일이나 구글로 가입하고, 운영자가 역할을 부여합니다.
- `clubs/{club}/roles/{uid}` 에 `member`도 들어갑니다.
- 규칙: `kv/members` 읽기는 roles 문서가 있는 사람만.

무엇이 해결되나
- ✅ 위 전부 + **회원 명단 읽기까지** 막힙니다.
- ✅ 기록·통계도 같은 방식으로 잠급니다.

비용
- ❌ **입장 흐름이 근본적으로 바뀝니다.** 지금은 "이름 고르고 한 글자".
  앞으로는 "이메일 인증하고 운영자 승인 기다리기". 체육관에서 처음 온
  사람에게 이걸 시키는 것은 이 앱이 지금까지 지켜 온 방향과 정반대입니다.
- ❌ 계정 없는 어르신·손님이 많은 동호회에서는 운영이 막힙니다.
- 앱 변경 범위: 입장·가입·승인 흐름 전체. 큼.

### 갈래 C — 운영자만 계정 + 명단 읽기는 Functions로

- 갈래 A를 하고, 거기에 더해 **`kv/members` 직접 읽기를 규칙으로 막습니다.**
- 앱은 대신 `listMembers` 함수를 부릅니다. 서버가 판단해서 내려 줍니다.
  - 게스트 → 아무것도 안 내려줌
  - 회원 입장 화면 → **가려진 이름만**(`김철○`)
  - 운영자 계정 → 전체

무엇이 해결되나
- ✅ 갈래 A 전부 + 회원 명단 읽기까지.
- ✅ 회원은 여전히 계정이 필요 없습니다.

비용
- ❌ **명단이 오프라인에서 안 읽힙니다.** 지금은 Firestore 캐시 덕분에
  인터넷이 끊겨도 명단이 남아 있습니다. 함수 호출은 캐시가 없습니다.
  체육관 와이파이가 불안하면 회원 입장 화면이 안 뜹니다.
  → 완화: 가려진 이름 목록만 로컬에 캐시. 그래도 첫 접속은 온라인 필요.
- ❌ 명단 쓰기 경로(추가·수정·삭제·CSV·복원)도 전부 함수로 옮겨야 합니다.
  안 그러면 읽기만 막고 쓰기는 열린 이상한 상태가 됩니다.
- 앱 변경 범위: 큼. `main.js` 부팅, `gate.js`, `screens.js`, `actions.js`.

## 추천 — A 먼저, C는 나중에

**갈래 A를 먼저 하십시오.** 이유는 셋입니다.

1. 지금 가장 구체적으로 위험한 것이 "운영자 비밀번호를 아는 사람이 앱을
   우회해 명단을 통째로 바꾸는 것"입니다. A가 그걸 끝냅니다.
2. 회원 경험이 하나도 안 바뀝니다. 되돌리기도 쉽습니다.
3. **C는 A 위에 얹는 것**이라 순서가 낭비되지 않습니다. A를 해 두면
   나중에 C로 갈 때 규칙과 역할 구조를 그대로 씁니다.

**갈래 B는 권하지 않습니다.** 이 앱이 지금까지 옳게 지켜 온 것 — 체육관에서
빨리, 계정 없이 — 을 버리는 대가로 얻는 것이 C와 같습니다. C가 더 낫습니다.

명단 읽기 보호가 지금 당장 급하다면 A와 C를 이어서 하면 됩니다. 다만 C의
**오프라인 대가는 실제로 아픕니다** — 지하 체육관에서 회원 입장이 안 되는
날이 생깁니다. 그걸 감수할지가 판단의 핵심입니다.

## 갈래 A를 하면 무엇이 바뀌나

### 콘솔에서 (사용자)

1. Authentication → 로그인 방법 → **이메일/비밀번호** 또는 **Google** 켜기
   (익명은 **그대로 켜 둡니다** — 회원·게스트가 계속 씁니다)
2. 소유자 본인 계정으로 한 번 로그인
3. 콘솔에서 `clubs/teambailey/roles/{그 uid}` = `{ role: 'owner' }` 생성
   - 첫 소유자는 콘솔로 심습니다(닭과 달걀 문제). 이후 운영자 추가는
     소유자가 앱에서 합니다.

### 규칙 (사용자가 붙여넣기)

```
function roleOf(club) {
  return request.auth != null
    ? get(/databases/$(database)/documents/clubs/$(club)/roles/$(request.auth.uid)).data.role
    : null;
}
function isOwner(club) { return hasRole(club) && roleOf(club) == 'owner'; }
function isStaff(club) { return hasRole(club) && roleOf(club) in ['owner','admin']; }
```

- `kv/members` 쓰기 중 **통째 교체**는 `isOwner(club)` 필요
- `roles/{uid}` 쓰기는 `isOwner(club)` 만
- 나머지 kv 쓰기는 지금처럼 익명도 허용(대진 운영은 회원도 함)

### 앱

- `secret.js` — probe/PBKDF2 구조를 **소유자·운영자 경로에서 걷어냅니다.**
  당장 지우지는 않습니다(계정이 없는 동호회가 남아 있을 수 있으므로
  한동안 둘 다 받습니다).
- `auth.js` — `loginAs(kind, pin)` 옆에 `loginWithAccount()` 추가.
  역할은 localStorage가 아니라 **roles 문서**에서 옵니다.
- `gate.js` — 소유자·운영자 버튼이 비밀번호 칸 대신 로그인 화면으로.

### 이관 중 주의

기존 동호회에는 roles 문서가 없습니다. 규칙을 먼저 조이면 **그 순간
운영자가 잠깁니다.** 순서를 지켜야 합니다.

1. 앱을 먼저 배포(계정 로그인과 비밀번호 로그인을 **둘 다** 받는 상태)
2. 소유자가 계정으로 한 번 들어와 roles 문서를 만든다
3. 그 뒤에 규칙을 조인다
4. 한동안 지켜본 뒤 비밀번호 경로를 걷어낸다
