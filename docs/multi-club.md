# 여러 동호회 · 유료 멤버십 — 구조 설계

이 문서는 두 가지를 다룹니다.

1. **여러 동호회를 한 배포본에서 운영**하고 URL 경로로 구분하는 구조 — *일부 구현됨*
2. **유료 멤버십**으로 동호회 등록을 과금하는 구조 — *설계만, 미구현*

구현 상태를 각 절 머리에 표시했습니다. 지어낸 것과 실제로 도는 것을 섞지
않으려는 것이니, 없는 기능을 있다고 읽지 마세요.

---

## 1. 여러 동호회

### 1.1 지금 되는 것 ✅ 구현됨

주소의 첫 조각이 동호회 식별자입니다.

```
/                    → default   (지금까지 쓰던 그 동호회. 주소가 안 바뀝니다)
/hanul/              → hanul
/hanul/아무거나       → hanul
/manual.html         → default   (실제 파일이므로 동호회로 보지 않습니다)
```

`js/store.js`의 `CLUB`이 `location.pathname`에서 이 값을 뽑고, 그 아래가 통째로
갈라집니다.

| | 경로 |
|---|---|
| Firestore | `clubs/{CLUB}/kv/...`, `clubs/{CLUB}/secret/...` |
| 이 기기 저장소 | `bmt:{CLUB}:...` |
| 운영자 비밀번호 | `clubs/{CLUB}/kv/adminAuth` + `clubs/{CLUB}/secret/adminPin` |

보안 규칙은 처음부터 `clubs/{club}` 와일드카드라 새 동호회에도 그대로 걸립니다.
**동호회마다 운영자 비밀번호가 따로**이고, 서로의 명단·기록을 볼 수 없습니다.

식별자 규격은 `^[a-z0-9][a-z0-9-]{1,30}$` — 소문자·숫자·하이픈, 2~31자입니다.
벗어나면 `default`로 떨어집니다. 경로 조각이 그대로 Firestore 문서 ID가 되므로
`..`이나 슬래시가 섞이면 안 되고, 낯선 주소로 들어온 사람이 빈 동호회를
새로 만들어 버리는 것도 막아야 하기 때문입니다.

**모든 자산 경로는 절대 경로여야 합니다** (`/js/...`, `/css/...`).
상대 경로로 두면 `/hanul/`에서 `/hanul/js/store.js`를 찾는데 그런 파일은 없고,
호스팅 rewrite가 그 요청을 `index.html`로 되돌려 스크립트 자리에 HTML이
실립니다. 앱이 조용히 죽습니다. 실제로 한 번 밟은 함정입니다.

### 1.2 아직 없는 것 ❌ 미구현

지금은 **아무 주소나 치면 그 이름의 빈 동호회가 생깁니다.** `/aaa/`로 들어가면
운영자 비밀번호 설정 화면이 뜨고, 설정하면 그게 `aaa` 동호회가 됩니다.
등록 절차도, 목록도, 소유자도 없습니다.

제대로 하려면 **동호회 등록부**가 필요합니다.

```
clubs/{clubId}/meta      { name, ownerUid, createdAt, plan, status }
directory/{clubId}       { name, exists:true }        ← 목록용, 읽기 공개
```

규칙:

```
match /clubs/{club}/{document=**} {
  allow read, write: if exists(/databases/$(db)/documents/clubs/$(club)/meta)
                     && get(...).data.status == 'active'
                     && ...(기존 조건)
}
```

즉 **`meta`가 없는 동호회에는 아무것도 못 쓴다.** 그러면 아무 주소나 쳐서
동호회를 만드는 길이 막히고, 등록은 아래 3절의 경로로만 열립니다.

`/`에는 동호회 고르기 화면을 둡니다 — `directory`를 읽어 목록을 보여 주고,
최근에 쓴 동호회는 이 기기에 기억해 두었다가 바로 넘겨줍니다.

### 1.3 왜 서브도메인이 아니라 경로인가

| | 경로 `/hanul/` | 서브도메인 `hanul.앱.com` |
|---|---|---|
| 배포 | 지금 그대로 | 와일드카드 DNS + 인증서 |
| Firebase Hosting | rewrite 한 줄 | 사이트를 여러 개 만들거나 프록시 |
| 저장소 격리 | 같음 (경로가 다름) | 같음 |
| localStorage 격리 | 키 접두어로 직접 (지금 방식) | 브라우저가 오리진 단위로 자동 |
| 보기 좋은 정도 | 보통 | 좋음 |

동호회 서른 개 규모에서 서브도메인 값을 치를 이유가 없습니다. 나중에 필요해지면
`CLUB` 뽑는 함수 하나만 고치면 되도록 한 곳에 모아 뒀습니다.

## 2. 유료 멤버십 ❌ 설계만, 미구현

### 2.1 클라이언트만으로는 불가능합니다

지금 앱에는 서버가 없습니다. 브라우저에서 도는 코드와 Firestore 규칙이 전부입니다.
그 상태로 과금을 붙이면 이렇게 됩니다.

- 결제 여부를 클라이언트가 판단 → 개발자 도구로 `plan='pro'` 한 줄이면 끝
- 가격을 클라이언트가 계산 → 요청을 고쳐서 100원 결제
- 구독 만료를 클라이언트가 확인 → 시계를 되돌리면 끝

**결제는 반드시 서버가 확인해야 합니다.** Cloud Functions(또는 Cloud Run) 하나가
필요하고, 그때부터는 무료 요금제(Spark)가 아니라 **Blaze 요금제**여야 합니다.

### 2.2 최소 구성

```
                결제사(토스페이먼츠·아임포트·Stripe)
                    │  ① 결제창
   [브라우저] ───────┤
        │           │  ② 웹훅(서버→서버, 서명 검증)
        │           ▼
        │      [Cloud Functions]
        │           │  ③ 이 경로로만 씀
        ▼           ▼
     Firestore  clubs/{clubId}/meta { plan, paidUntil, status }
                            ↑
                   규칙: 클라이언트 쓰기 전면 금지
```

핵심은 하나입니다. **`meta` 문서는 클라이언트가 절대 못 쓴다.**

```
match /clubs/{club}/meta {
  allow read: if true;                 // 상태는 봐도 된다
  allow write: if false;               // Functions(관리자 SDK)만 규칙을 우회한다
}
```

관리자 SDK는 규칙을 통과하지 않으므로, `allow write: if false`여도 Functions는
씁니다. 클라이언트는 못 씁니다. 이 한 줄이 과금의 전부입니다.

### 2.3 요금제 예시

| | 무료 | 동호회 | 리그 |
|---|---|---|---|
| 동호회 수 | 1 | 1 | 5 |
| 회원 | 30명 | 무제한 | 무제한 |
| 코트 | 2면 | 8면 | 8면 |
| 기록 보관 | 30일 | 3년 | 3년 |
| 운영자 동시 접속 | 1 | 2 | 5 |

제한을 **규칙에서** 겁니다. 클라이언트에서 숨기는 것은 안내일 뿐 제한이 아닙니다.

```
function plan(club) { return get(/…/clubs/$(club)/meta).data; }
function paid(club) { return plan(club).status == 'active'
                          && plan(club).paidUntil > request.time; }

// 무료 요금제는 코트 2면까지 — settings 문서 크기가 아니라 실제 값으로 걸려면
// 값 검증이 필요하므로, 실무에서는 Functions가 settings를 검사하고 meta에
// limits를 박아 두는 편이 규칙을 단순하게 만든다.
allow update: if docId != 'members' || paid(club)
                 || request.resource.data.v.size() < 3000;   // ≒ 30명
```

### 2.4 결제 흐름

1. 운영자가 **동호회 만들기** → Functions `createClub` 호출
   - 식별자 중복 확인, `meta`를 `{plan:'free', status:'active'}`로 생성
   - `directory/{clubId}` 등록
2. **업그레이드** → Functions `createCheckout`이 결제사 세션을 만들고 URL 반환
   - 가격은 **서버가** 정합니다. 클라이언트가 보낸 금액은 무시합니다.
3. 결제 완료 → 결제사가 **웹훅**으로 Functions 호출
   - 서명 검증 → `meta.plan`, `meta.paidUntil` 갱신
   - 브라우저가 알려 주는 결제 성공은 신뢰하지 않습니다(위조 가능)
4. **갱신·해지** → 웹훅으로 같은 문서 갱신. 만료되면 `status:'past_due'`
5. 매일 도는 스케줄 함수가 `paidUntil`이 지난 동호회를 `expired`로 바꿉니다

### 2.5 만료되면 무엇을 하나

**데이터를 지우지 않습니다.** 읽기는 열어 두고 쓰기만 막습니다.

- 대진판·기록 보기 ○
- 새 경기 배정, 회원 추가 ✕
- 백업 내려받기 ○ ← 이건 반드시 열어 둡니다. 돈을 안 냈다고 그 동호회의
  명단과 기록을 인질로 잡으면 안 됩니다.

### 2.6 먼저 결정해야 할 것들

구현 전에 답이 있어야 하는 것들입니다. 기술이 아니라 사업 쪽 결정입니다.

- **결제사**: 국내 동호회 대상이면 토스페이먼츠나 아임포트(카카오페이·계좌이체).
  Stripe는 국내 카드 처리가 번거롭습니다.
- **과금 단위**: 동호회당 월정액이 가장 단순합니다. 회원 수 종량제는 계산과
  분쟁이 늘어납니다.
- **누가 내는가**: 운영자 한 명이 내는지, 회원들이 나눠 내는지. 후자면
  개인 계정과 정산이 필요해져 규모가 몇 배가 됩니다.
- **환불·세금계산서**: 국내 사업자라면 전자세금계산서 요구가 반드시 들어옵니다.
- **실제 로그인**: 과금하는 순간 "이 동호회의 주인이 누구인가"가 확정되어야
  합니다. 익명 로그인으로는 소유권을 증명할 수 없으므로 **Google 로그인
  도입이 선행 조건**입니다. 이건 아래 3절과 같은 작업입니다.

## 3. 같이 따라오는 것 — 실제 로그인

지금은 익명 로그인이라 규칙이 "누가" 요청했는지 모릅니다. 그래서:

- 회원 명단 읽기를 막을 수 없습니다(입장 화면의 이름 가리기는 눈가림일 뿐입니다)
- 동호회 소유자를 증명할 수 없습니다
- 운영자 비밀번호를 온라인 무차별 대입으로 두드리는 것을 막을 수 없습니다

멀티 동호회까지는 익명으로 버틸 수 있지만, **과금은 못 버팁니다.**
Google 로그인 + `clubs/{club}/roles/{uid}` 역할 문서로 가면 위 셋이 한꺼번에
풀리고, 지금의 비밀번호 구조(`secret/adminPin` + `probe`)는 그때 통째로
들어냅니다 — 익명 로그인 시대의 임시 방편이기 때문입니다.

## 4. 순서 제안

| 단계 | 내용 | 규모 |
|---|---|---|
| 0 ✅ | 경로로 동호회 가르기, 동호회별 운영자 비밀번호 | 완료 |
| 1 | `meta` 문서 + 규칙 게이트(등록 안 된 동호회는 쓰기 금지) | 작음 |
| 2 | `/` 동호회 고르기·만들기 화면, `directory` | 중간 |
| 3 | Google 로그인 + 역할 문서 (익명 로그인 졸업) | 큼 |
| 4 | Cloud Functions + 결제사 웹훅 + 요금제 제한 | 큼 |

1·2단계는 지금 구조 위에서 바로 얹을 수 있습니다. 3단계는 보안 모델을 바꾸는
일이라 규칙과 입장 화면을 다시 씁니다. 4단계는 3단계가 끝나야 시작할 수 있습니다.
