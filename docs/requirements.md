## 0. 이 문서에 대하여

지금은 한 동호회가 쓰는 단일 배포본입니다. 이 문서는 그것을 **여러 나라의 여러
동호회가 돈을 내고 쓰는 서비스**로 만들 때 무엇이 필요한지를 적습니다.

읽는 법:

| 표기 | 뜻 |
|---|---|
| **필수** | 이게 없으면 유료 서비스가 성립하지 않습니다 |
| **권장** | 없어도 굴러가지만 없으면 곧 후회합니다 |
| **선택** | 나중에 판단 |
| 🔵 | 지금 이미 되는 것 |
| ⚠ | 결정이 필요한 것 (§12에 모아 뒀습니다) |

**지어낸 숫자를 넣지 않았습니다.** 목표 수치는 전부 *제안*이며, 사업 계획이
정해지면 바꿔야 합니다. 근거 없이 확정된 것처럼 읽지 마세요.

> 않고 Firestore를 직접 두드리면 운영자도 명단을 갈아끼울 수 있습니다.
> 그것까지 막으려면 실제 로그인이 필요합니다(§11 2단계).

**#11**(프로모션 후 동작). 과금을 미루기로 했으므로 #3은 유료 전환 시점까지
미뤄도 됩니다.

> **결제를 미루는 것이 설계를 미루는 것은 아닙니다.** 무료로 열어도
> `meta.plan` · `meta.paidUntil` · `meta.status`는 **처음부터 넣습니다.**
> 나중에 값만 채우면 되게 하고, 지금은 전부 `plan:'promo'`로 둡니다.
> 이 필드들을 나중에 추가하려면 이미 만들어진 모든 동호회를 손봐야 합니다.

## 1. 지금 상태 — 정직한 진단

### 1.1 잘 도는 것 🔵

- 체육관 현장 운영에 필요한 것은 거의 다 됩니다. 자동 배치, 더블탭·드래그,
  선입선출, 오프라인 내성, 실시간 동기화, 회원 명단 보호.
- **오프라인이 진짜로 됩니다.** 체육관 와이파이는 믿을 게 못 되는데, 지금 앱은
  끊겨도 계속 조작되고 돌아오면 맞춰집니다. 이건 지키면서 가야 합니다.
- 동호회별 경로 분리(`/hanul/`)와 동호회별 운영자 비밀번호.

### 1.2 지금 구조로는 못 버티는 것

**(가) 데이터가 JSON 덩어리입니다**

모든 저장이 `clubs/{club}/kv/{docId}` 문서 하나에 `{v: "…JSON 문자열…"}` 형태로
들어갑니다. 세션 문서 하나에 출석·코트·대기열·경기기록·이력이 통째로 들어 있습니다.

여기서 나오는 문제:

1. **질의가 불가능합니다.** "홍길동이 지난 3개월 동안 몇 경기 쳤나"를 물으려면
   모든 세션 문서를 내려받아 브라우저에서 세야 합니다.
2. **동시 쓰기가 서로를 지웁니다.** 운영자 두 명이 같은 순간 조작하면 나중 쓰기가
   앞 쓰기를 통째로 덮습니다. 지금은 1.5초 에코 필터로 눈속임하고 있을 뿐입니다.
3. **1 MiB 문서 한도.** 회원 수천 명 또는 하루 경기 수백 건이면 닿습니다.
4. **필드 단위 권한이 없습니다.** JSON 문자열 안은 규칙이 들여다볼 수 없어서,
   "회원 이름만 감추기" 같은 것이 원천적으로 불가능합니다.

**(나) 익명 로그인**

규칙이 "누가" 요청했는지 모릅니다. 그래서 회원 명단 읽기를 막을 수 없고,
동호회 소유권을 증명할 수 없고, 따라서 **과금할 수 없습니다.** 돈을 받으려면
"이 동호회의 주인이 누구인가"가 확정돼야 합니다.

**(다) 단일 리전**

Firestore 데이터베이스는 만들 때 위치를 정하면 **바꿀 수 없습니다.** 지금은
`asia-northeast2`(오사카) 하나입니다. 유럽·미주 사용자는 매 요청마다 태평양을
왕복합니다.

**(라) 배포가 클라이언트 전용**

서버가 없습니다. 결제 확인, 웹훅 수신, 예약 작업, 관리자 도구를 놓을 곳이
없습니다.

## 2. 목표와 비목표

### 2.1 목표

1. 여러 동호회가 서로 격리된 채 한 서비스를 씁니다.
2. **글로벌 서비스입니다.** 나라를 넘어가도 현장 조작이 즉각 반응합니다.
3. 개인정보가 **그 나라 밖으로 나가지 않게** 할 수 있습니다.
4. 구독 결제가 서버에서 검증됩니다.
5. 웹과 모바일 앱이 같은 백엔드를 씁니다.
6. **오프라인 내성을 잃지 않습니다.** 이게 이 앱의 핵심 가치입니다.

### 2.2 비목표 (이번 범위 아님)

- 대회 운영(토너먼트 대진표, 시드, 라운드 로빈)
- 결제 정산·회계 시스템 (결제사에 맡깁니다)
- 실시간 영상·채팅
- 다른 종목(테니스·탁구) — 구조는 열어 두되 이번엔 안 합니다

### 5.2.1 신규 동호회 신청 — 대표 주소에서

아무 경로나 쳐서 동호회가 생기는 길은 막혔습니다. 대신 **대표 주소(`/`)
하단의 신청 링크**로만 만들 수 있습니다.

| ID | 요구사항 | 등급 |
|---|---|---|
| FR-R1 | 대표 주소 하단에 **새 동호회 신청** 링크 | **필수** |
| FR-R2 | 신청 입력: 동호회 이름(한글) · **영문 이름**(주소가 됨) · 연락처 · 간단 소개 | **필수** |
| FR-R3 | 영문 이름은 주소 규격(`^[a-z0-9][a-z0-9-]{1,30}$`)이며 **중복 즉시 확인** | **필수** |
| FR-R4 | **전체 정원 상한(100개)** — 벌크 가입 차단 🔵(규칙·문서 준비됨) | **필수** |
| FR-R4b | 캡차 — 정원을 늘릴 때 다시 검토 | **선택** (보류) |
| FR-R5 | 신청 내용을 신청 DB에 남김 (승인 여부와 무관하게 기록) | **필수** |
| FR-R6 | 캡차를 통과하면 **즉시** 동호회를 개설, 프로모션 기간 부여 | **필수** |
| FR-R7 | 개설 직후 운영자 비밀번호를 정하는 화면으로 바로 넘김 | **필수** |
| FR-R8 | 연락처로 개설 안내 발송 (주소·초기 안내) | **권장** |

**즉시 개설입니다.** 사람이 승인하는 절차를 두지 않습니다 — 신청하고 기다리는
경험은 첫인상을 망치고, 우리 쪽 처리 부담도 큽니다.

### 5.2.1a 전체 동호회 정원 — 캡차 대신 🔵

캡차는 보류하고, **전체 동호회 수 상한**을 남용 방지 장치로 씁니다.

```
registry/clubs = { count: 3, limit: 100 }
```

- **읽기 공개** — 앱이 "정원이 찼습니다"를 보여 줄 수 있어야 합니다 🔵
- **쓰기는 아무에게도 열려 있지 않습니다** — 관리자 SDK(서버·콘솔)만 🔵
- 앱은 없는 주소로 들어온 사람에게 현재 `count / limit`을 보여 줍니다 🔵

**왜 캡차보다 이게 나은가**: 캡차는 지역에 따라 통째로 막히고(§12 #10), 서버
검증이 필요하며, 뚫는 서비스도 있습니다. 100개 상한은 **정확히 100개**를
보장하고, 넘으면 무슨 수를 써도 더 못 만듭니다. 규모가 커지면 그때 캡차를
붙이고 상한을 올립니다.

> ⚠ **상한을 지키는 주체는 개설하는 쪽입니다.** 지금은 개설이 수동(콘솔)이므로
> **동호회를 만들 때 `count`를 함께 올리는 것이 운영 절차**입니다. Functions가
> 생기면 읽고-올리고-만들기를 한 트랜잭션으로 묶어 자동으로 강제합니다.
> 규칙은 `registry/clubs`를 클라이언트가 못 고치게 막는 데까지만 합니다 —
> 문서 개수를 세는 것은 보안 규칙이 할 수 있는 일이 아닙니다.

⚠ **개설 자체는 여전히 Cloud Functions가 필요합니다** — 영문 이름 중복 확인과
`meta/club` 생성을 클라이언트에 열어 주면 등록 게이트가 무의미해집니다.

```
신청 폼 ──캡차 토큰──▶ createClub (Functions)
                          │ ① 캡차를 캡차 제공자에게 서버-대-서버로 검증
                          │ ② 영문 이름 중복 확인 (트랜잭션)
                          │ ③ clubs/{id}/meta/club 생성
                          │      { name, nameEn, contact, about,
                          │        region, plan:'promo',
                          │        promoUntil: 오늘+30일, status:'active' }
                          │ ④ directory/{id} 등록
                          │ ⑤ clubApplications/{id}에 신청 원본 보존
                          ▼
                    /{영문이름}/ 으로 이동 → 운영자 비밀번호 설정
```

`clubApplications`는 개설과 별개로 **남겨 둡니다.** 남용 조사, 연락처 확인,
분쟁이 생겼을 때 "누가 무엇으로 신청했는지"가 필요합니다.

### 5.2.2 대표 주소(`/`)의 첫 화면

지금은 `/`가 곧 `default` 동호회입니다. 글로벌로 가면 `/`는 **현관**이어야 합니다.

| ID | 요구사항 | 등급 |
|---|---|---|
| FR-H1 | **클럽 코드** 입력칸 하나로 시작 | **필수** |
| FR-H2 | 입력한 코드의 동호회 존재 여부를 확인 | **필수** |
| FR-H3 | 있으면 `/{코드}/` 로 이동 | **필수** |
| FR-H4 | 없으면 "없는 주소" 안내 + 신청 링크 | **필수** 🔵 |
| FR-H5 | 마지막에 쓴 동호회를 기억해 다음부터 바로 넘김 | **권장** |
| FR-H6 | 하단에 **새 동호회 신청** 링크 (§5.2.1) | **필수** |

동호회에 들어간 뒤 역할을 고르는 흐름은 지금과 같되, 소유자가 추가됩니다.

| 고른 역할 | 확인 절차 |
|---|---|
| **소유자** | **소유자 비밀번호** — 운영자와 다른 값 🔵 |
| **운영자** | 관리 비밀번호 🔵 |
| **회원** | 이름 선택 + 가려진 글자 확인 🔵 |
| **게스트** | 확인 없음. 대진판만, 이름은 **성만** 🔵 |

**소유자만 되는 것** 🔵 — 지금은 하나입니다: **회원 명단을 통째로 바꾸는 조작**
(백업 복원 · CSV 일괄등록 · 클라우드에서 다시 불러오기). 되돌릴 수 없고 모든
기기에 즉시 퍼지는, 이 앱에서 가장 파괴적인 동작이라 소유자에게 둡니다.
그 밖의 경기 운영·설정·회원 개별 수정은 운영자도 그대로 합니다.

저장 구조는 운영자 비밀번호와 완전히 같습니다 — `kv/ownerAuth`(salt, 읽기 가능)
+ `secret/ownerPin`(해시, 읽기 금지) + probe 대조. 규칙 테스트가 **운영자 해시로는
소유자 확인이 통과되지 않는다**는 것을 확인합니다.

> **한계.** 규칙은 여전히 둘을 구분하지 못합니다. 앱을 거치지 않고 Firestore를
> 직접 두드리면 운영자 비밀번호를 아는 사람도 명단을 갈아끼울 수 있습니다.
> 이 구분은 **앱 안에서만** 유효합니다. 규칙 수준의 구분에는 실제 로그인이
> 필요합니다(§11 2단계).
>
> 소유자 비밀번호를 아직 정하지 않은 동호회에서는 관리 비밀번호로 대신 확인하고
> **그 사실을 화면에 알려 줍니다** — 안 그러면 기존 동호회의 복원 기능이 통째로
> 막힙니다.

**게스트에게 보이는 이름** 🔵 — 성만 남기고 가립니다(`김철수 → 김○○`).
누가 치고 있는지는 알 수 있으면서 명단이 통째로 새지는 않게 하는 절충입니다.

> 입장 화면의 가리기와 **방향이 반대**입니다. 거기는 본인 확인용이라 마지막
> 글자를 가리고(`김철수 → 김철○`), 여기는 남에게 안 보이는 것이 목적이라
> 첫 글자만 남깁니다. 두 글자 성(남궁·선우)은 한 글자로 잘리는데, 가리는 쪽이
> 목적이라 덜 보이는 것은 문제가 아닙니다.

## 6. 데이터 모델

### 6.1 설계 원칙

1. **동호회 간 조인이 없습니다.** 이 워크로드는 완벽하게 샤딩 가능합니다 —
   지리적 분산이 자연스러운 이유입니다.
2. **자주 바뀌고 함께 읽는 것은 한 문서에.** 보드가 그렇습니다.
3. **질의해야 하는 것은 문서 하나에 하나씩.** 회원과 경기 기록이 그렇습니다.
4. **돈과 권한은 클라이언트가 못 씁니다.**

### 6.2 전역 (모든 리전에서 읽음)

```
directory/{clubId}
  { name, region, status, plan, memberCount, updatedAt }

clubApplications/{applicationId}
  { nameKo, nameEn, contact, about, ip, at, result, clubId? }
    ← 신청 원본. 개설과 별개로 보존한다(남용 조사·분쟁 대비).
      클라이언트는 못 읽는다. 서버만.
```

- **읽기 공개, 쓰기는 서버만.** 앱이 부팅할 때 `clubId → region`을 여기서 찾습니다.
- 거의 안 바뀌므로 **엣지에서 캐시**합니다(TTL 60초 수준).
- 이름 검색·동호회 찾기도 여기서 합니다.

```
users/{uid}
  { displayName, email, locale, createdAt }
users/{uid}/memberships/{clubId}
  { role: owner|admin|member, clubRegion, joinedAt }
```

- 로그인 직후 "내가 속한 동호회"를 한 번에 알기 위해 전역에 둡니다.

### 6.3 동호회별 (홈 리전에 저장)

```
clubs/{clubId}/meta/club                              ← 등록 표시이자 과금의 진실 원천
  { name, nameEn, ownerUid, region,
    plan: 'promo'|'free'|'club'|'league',
    status: 'active'|'promo'|'past_due'|'expired',
    promoUntil, paidUntil, limits, contact, createdAt }
                  ← 클라이언트 쓰기 금지 🔵. 읽기는 공개(앱이 안내를 띄우려면 필요).
                    이 문서가 없으면 규칙이 그 동호회의 모든 접근을 거절한다 🔵.

clubs/{clubId}
  settings      { 코트수, 대기슬롯, 가중치, 급수정의, locale, timezone }
                  ← 운영자 쓰기 가능

clubs/{clubId}/members/{memberId}
  { name, gender, birthYear, grade, active, userUid?, joinedAt, lastSeen }
                  ← 1문서 = 1명. 질의 가능, 크기 한도 없음, 동시 수정 안전

clubs/{clubId}/joinRequests/{reqId}
  { name, gender, birthYear, grade, byUid, at, status }

clubs/{clubId}/sessions/{yyyy-mm-dd}
  { startedAt, endedAt, closedBy, stats }              ← 세션 헤더(작고 안정적)

clubs/{clubId}/sessions/{yyyy-mm-dd}/board/current
  { courts[], queues[], pool[], rev, updatedAt }       ← 실시간 상태. 자주 씀.

clubs/{clubId}/matches/{matchId}
  { sessionDate, court, type, startedAt, endedAt,
    players:[{memberId,name,team}], playerIds:[…] }    ← 1문서 = 1경기

clubs/{clubId}/attendance/{yyyy-mm-dd}/people/{memberId}
  { games, lastEnd, checkedInAt }
```

### 6.4 왜 이렇게 쪼개나

| 컬렉션 | 쓰기 빈도 | 왜 이 모양인가 |
|---|---|---|
| `board/current` | **높음** (조작마다) | 한 덩어리로 원자적이어야 하고, 모든 기기가 같은 것을 미러링합니다. 문서 하나가 맞습니다. |
| `members/*` | 낮음 | 쪼개야 질의되고, 두 운영자가 다른 회원을 동시에 고쳐도 안 부딪힙니다 |
| `matches/*` | 경기당 2회 | 개인별 통계·기간 조회의 대상. `playerIds` 배열에 `array-contains` 인덱스 |
| `meta/club` | 아주 낮음 🔵 | 과금의 진실 원천이자 **등록 표시**. 클라이언트 쓰기 금지 |

### 6.5 동시 편집 (FR-B1)

`board/current`에 **`rev` 정수**를 둡니다.

- 쓰기는 트랜잭션으로: 읽은 `rev`와 같을 때만 `rev+1`로 씁니다.
- 다르면 → 최신을 다시 읽고, **내 조작만** 다시 적용한 뒤 재시도합니다.
- 지금처럼 상태 전체를 통째로 덮지 않습니다.

> ⚠ **Firestore 단일 문서는 지속 쓰기 약 1회/초가 한계입니다.** 코트 8면을
> 바쁘게 돌리면 닿을 수 있습니다. 닿으면 `board/current` 하나 대신
> `board/court-{n}` + `board/queue`로 쪼갭니다. **처음부터 쪼개지는 마세요** —
> 원자성을 잃고 화면이 찢어져 보입니다. 실측 후 판단할 일입니다.

### 6.6 마이그레이션

기존 `kv/*` JSON 덩어리 → 새 컬렉션. 서버 배치로 한 동호회씩 변환하고,
변환이 끝난 동호회만 새 클라이언트를 받도록 `meta.schemaVersion`으로 가릅니다.
**되돌릴 수 있어야 합니다** — 변환 전 원본을 그대로 남겨 둡니다.

| NFR-S3 | 비밀은 어떤 클라이언트 번들에도 넣지 않음 |
| NFR-S4 | 전송 구간 TLS, 저장 시 암호화 (관리형 기본) |
| NFR-S5 | 규칙 변경은 **에뮬레이터 테스트 통과 후에만** 배포 |

> NFR-S5는 이미 한 번 값을 했습니다. "초기화하면 영영 로그인 불가"가 되는
> 규칙 버그를 에뮬레이터 테스트가 잡았습니다. 눈으로 읽어서는 못 봤을 것입니다.

## 8. 인프라 — 글로벌 분산

### 8.1 핵심 판단

**이 워크로드는 동호회 단위로 완벽히 격리됩니다.** 동호회 A의 데이터를 동호회 B와
조인할 일이 영원히 없습니다. 그래서 "글로벌 분산 DB"라는 어려운 문제를 풀 필요가
**없습니다.** 그냥 **동호회를 홈 리전에 못 박으면** 됩니다.

이게 이 설계에서 가장 중요한 문장입니다. 이것 때문에:

- 다중 마스터 복제, 충돌 해소, 전역 합의 — 전부 필요 없습니다
- 데이터 주권 요구가 지연 시간 최적화와 **같은 방향**입니다
- 리전을 늘리는 것이 단순 증설입니다

### 8.2 구성

```
                    ┌──────────────────────────────┐
   전 세계 사용자 ──▶│  CDN / 엣지 (Firebase Hosting) │  정적 자산, 엣지 캐시
                    └───────────────┬──────────────┘
                                    │  clubId → region 조회 (캐시됨)
                    ┌───────────────▼──────────────┐
                    │  directory (전역, 다중 리전)   │  개인정보 없음
                    └───────────────┬──────────────┘
                 ┌──────────────────┼──────────────────┐
                 ▼                  ▼                  ▼
        ┌────────────────┐ ┌────────────────┐ ┌────────────────┐
        │ asia-northeast3│ │      eur3      │ │      nam5      │
        │     (서울)      │ │    (유럽)      │ │    (북미)      │
        │  clubs/*       │ │   clubs/*      │ │   clubs/*      │
        │  Functions     │ │   Functions    │ │   Functions    │
        └────────────────┘ └────────────────┘ └────────────────┘
```

### 8.3 리전을 어떻게 나누나

**Firestore 다중 데이터베이스**를 씁니다. 한 프로젝트 안에 여러 데이터베이스를
두고 각각 다른 리전에 놓을 수 있습니다.

| 데이터베이스 | 위치 | 담당 | 순서 |
|---|---|---|---|
| **`(default)`** | **nam5 (미국 다중 리전)** | `directory`, `users`, `clubApplications` — 전역 | **프라이머리** |
| `clubs-us` | nam5 | 북미 + 리전이 정해지지 않은 동호회 | 프라이머리와 함께 |
| `clubs-kr` | asia-northeast3 (서울) | 한국·일본 동호회 | 수요가 생기면 |
| `clubs-eu` | eur3 | 유럽 동호회 | GDPR 대상이 생기면 |

**프라이머리는 미국(`nam5`)입니다.** 전역 라우팅표와 신청 접수가 여기 삽니다.
`nam5`는 다중 리전이라 미국 안에서 자동 복제되고, 전 세계에서 접근하기에 가장
중립적인 위치입니다.

리전 데이터베이스는 **필요해질 때 붙입니다.** 처음부터 셋을 다 만들 이유가
없습니다 — 비어 있는 DB도 관리 대상이고, 붙이는 것은 나중에도 쉽습니다.
반대로 **동호회를 어느 DB에 넣을지는 개설 시점에 정해야** 하므로,
`meta.region` 필드는 처음부터 있어야 합니다(값이 당분간 전부 `us`여도).

> ⚠ **Firestore 데이터베이스의 위치는 만든 뒤 바꿀 수 없습니다.**
>
> 지금 운영 중인 DB는 `asia-northeast2`(오사카)입니다. 프라이머리를 미국으로
> 정했으므로 **새 프라이머리 DB를 미국에 만들고**, 오사카는 기존 `default`
> 동호회를 담은 채로 두거나 나중에 `clubs-kr`로 옮깁니다.
>
> **오사카를 지금 비우려 하지 마세요.** 지금 돌아가는 동호회가 거기 있고,
> 데이터 이전은 §11 3단계(모델 분리)와 함께 하는 편이 한 번에 끝납니다.
> 두 번 옮기지 않으려면 그때까지 그대로 둡니다.

### 8.4 라우팅

1. 브라우저가 `/hanul/`을 엽니다 → CDN에서 앱 셸 (엣지, 빠름)
2. 앱이 `directory/hanul`을 읽어 `region: 'kr'` 확인 (엣지 캐시, 보통 <100ms)
3. 그 리전의 Firestore에 연결
4. 결과를 로컬에 캐시 → 다음 접속부터는 1·2단계 없이 바로 3단계

**리전이 바뀌는 경우**(동호회 이전)는 드물므로, 캐시 불일치 시 한 번 더 조회하고
갱신하는 정도로 충분합니다.

### 8.5 서버 (Cloud Functions)

| 함수 | 리전 | 역할 |
|---|---|---|
| `createClub` | 전역 | 식별자 중복 확인, `meta`·`directory` 생성 |
| `createCheckout` | 전역 | 결제 세션 생성 (**가격은 서버가 정함**) |
| `paymentWebhook` | 전역 | 결제사 웹훅 수신, 서명 검증, `meta` 갱신 |
| `sendTurnPush` | 동호회 리전 | 보드 변경 트리거 → 내 차례 푸시 |
| `expireSubscriptions` | 전역 | 매일, 만료 처리 |
| `exportClubData` | 동호회 리전 | 데이터 내보내기 (개인정보가 리전을 안 넘게) |

> 개인정보를 만지는 함수는 **그 동호회의 리전에서 돌아야 합니다.** NFR-D1을
> 함수 배치로도 지켜야지, DB만 나눠 놓고 함수가 전역에서 읽으면 의미가 없습니다.

### 8.6 비용 감각

Firestore는 문서 읽기·쓰기 건당 과금입니다. 지금 구조에서 **쓰기 증폭**을
주의해야 합니다.

- 보드 문서 1회 쓰기 → 그 문서를 듣고 있는 기기 수만큼 **읽기** 과금
- 코트 3면 2시간 세션 ≈ 조작 500회, 기기 10대 → 쓰기 500 + 읽기 5,000
- 동호회당 세션 하나에 몇십 원 수준. **1,000개 동호회여도 부담은 아닙니다.**

문제가 되는 것은 오히려 **부주의한 전체 조회**입니다. "모든 동호회의 통계"
같은 화면을 만들면 즉시 비싸집니다. 집계는 미리 계산해서 `meta`에 박아 둡니다.

⚠ 실측 없이 확정하지 마세요. 위 숫자는 현재 코드 기준 어림입니다.

### 9.1 단계

> iOS 16.4부터 홈 화면에 추가한 PWA도 웹 푸시를 받습니다. 즉 **FR-N1(내 차례
> 알림)은 앱스토어 없이도 됩니다.** 앱스토어가 필요한 진짜 이유는 기술이 아니라
> **발견 가능성과 유료 서비스의 신뢰감**입니다.

### 9.2 앱스토어의 결제 문제 ⚠

**이게 사업 모델을 좌우합니다.**

- iOS 앱 **안에서** 디지털 구독을 팔면 Apple이 **인앱결제(수수료 15~30%)를
  요구**합니다.
- 웹에서만 팔고 앱은 이미 산 권한을 읽기만 하는 구성은 가능하지만, 앱 안에서
  결제 페이지로 유도하는 것에 제약이 있습니다(지역·시기에 따라 규정이 바뀝니다).
- Google Play도 유사하나 상대적으로 느슨합니다.

**결정이 필요합니다**: 웹 전용 결제로 갈지, 수수료를 감수하고 인앱결제를 넣을지.
매출의 15~30%짜리 결정이라 개발 착수 전에 정해야 합니다.

## 11. 단계별 계획

| 단계 | 내용 | 규모 | 선행 |
|---|---|---|---|
| **0** 🔵 | 경로 기반 동호회, 동호회별 비밀번호 | 완료 | — |
| **1** 🔵 | `meta/club` + 규칙 게이트, 게스트 이름 가리기 | 완료 | — |
| **1b** 🔵 | 소유자 비밀번호(운영자와 별개), 전체 정원 문서 | 완료 | 1 |
| **2** | 실제 로그인 (Google/Apple/Kakao) + 역할 문서 | **큼** | 1 |
| **3** | 데이터 모델 분리 (§6) + 마이그레이션 | **큼** | 2 |
| **4** | 동호회 만들기·찾기 화면, `directory` | 중간 | 1,2 |
| **5** | Cloud Functions + **신청 접수 · 캡차 · 개설** | **큼** | 4 |
| **5b** | 결제 (유료 전환 시점에) | **큼** | 5 |
| **6** | 리전 분리, 라우팅 | 중간 | 3,4 |
| **7** | PWA + 푸시 | 중간 | 2 |
| **8** | 앱스토어 등재 | 중간 | 7, §9.2 결정 |
| **9** | 국제화 | 중간 | — (병행 가능) |

**1단계는 끝났습니다** 🔵 — 아무 주소나 치면 동호회가 생기던 구멍이 닫혔고,
게스트에게는 이름이 성만 보입니다.

**다음은 4·5단계입니다.** 신규 동호회를 실제로 받으려면 대표 주소의 신청 폼과
그것을 처리할 서버가 필요합니다. **캡차 검증은 서버 없이는 불가능**하므로
(브라우저가 "통과했다"고 말하는 것을 믿으면 캡차가 없는 것과 같습니다)
4·5단계는 사실상 한 덩어리입니다. 결제를 미루기로 했으므로 5b는 뒤로 갑니다.

**2단계(로그인)가 여전히 병목입니다.** 소유자 인증과 회원 명단 프라이버시가
여기 묶여 있고, 넣는 순간 입장 화면·권한·규칙을 다시 씁니다. 다만 **과금을
미루기로 해서 급한 정도는 낮아졌습니다** — 로그인이 필수가 되는 가장 큰 이유가
"누구에게 청구하는가"였기 때문입니다.

### 지금 되는 것 vs 서버가 있어야 하는 것

| 지금 되는 것 | 서버(Functions)가 있어야 하는 것 |
|---|---|
| 등록 게이트 (규칙) 🔵 | 신청 폼 처리 · **캡차 검증** |
| 없는 주소 안내 🔵 | 동호회 개설 (`meta/club` 생성) |
| 게스트 이름 가리기 🔵 | 영문 이름 중복 확인 (트랜잭션) |
| `meta` 필드 설계 🔵 | 프로모션 만료 처리 (예약 작업) |
| 대표 주소 클럽 코드 입력 | 결제 · 웹훅 |
